# Moments 项目实现方案

> 本方案基于 `docs/moment 设计方案.md`，并结合需求澄清结果，将整个项目拆分为多个可独立交付的阶段。每个阶段都有明确的目标、任务清单和验收标准，便于增量开发与验证。

---

## 〇、需求澄清决策汇总

以下决策由需求方确认，作为本方案的实现约束：

| 议题 | 决策 |
|---|---|
| 主页信息流展示范围 | 全部公开动态 + 好友的「仅好友」动态 + 自己的全部动态（混合展示） |
| 默认头像 PNG | 由需求方提供文件，后端在 `assets/default_avatar.png` 内置分发 |
| 首次初始化判定 | 数据库 `system_status` 表记录 `initialized` 状态位；未初始化时前端进入初始化页，注册者成为 admin；初始化完成后该页不再出现 |
| 账号注销 | 用户可自助注销（不可恢复），内容保留展示；恢复账号只能联系管理员（管理员在后台手动改回 active） |
| 登录锁定 | 同一账号连续失败 5 次锁定 15 分钟，按账号维度计数（成功登录清零） |
| 前端密码加密 | 后端启动生成 RSA 密钥对，前端登录/注册页拉取公钥用 JSEncrypt 加密密码后传输；后端私钥解密后再 bcrypt 存储 |
| 评论区图片 | 每条评论最多 1 张图片，复用朋友圈图片的格式校验、大小限制与缩略图生成规则 |
| 分页方案 | 信息流使用 cursor-based（基于 `created_at` + `id` 游标）；评论列表使用 offset-based |
| 删除权限与方式 | 动态与评论均软删除（保留记录，标记 `deleted_at`）；删除权限：内容作者本人可删自己的动态/评论；动态作者可删其动态下任意评论；admin 可删任意内容 |
| 后台任务范围 | 仅媒体处理走 BackgroundTasks（缩略图、大图、视频首帧、WebP 转换）；上传接口同步落盘并返回，处理完成后可访问 |
| 点赞与通知 | 支持点赞/取消点赞（toggle）；本期不实现任何通知系统 |
| 链式评论展示 | 评论按时间平铺展示，回复评论时显示「回复 @xxx」引用，不缩进嵌套（类似微博） |

## 一、技术栈与版本约定

### 后端
- Python 3.12+
- 依赖管理：uv
- Web 框架：FastAPI
- ASGI 服务器：uvicorn + gunicorn worker（worker 数量 2）
- ORM：SQLAlchemy 2.x（async 暂不强制，先用同步 engine，便于后续切 PostgreSQL）
- 迁移：Alembic
- 数据库：SQLite（文件 `data/app.db`），通过 ORM 抽象便于切换
- 认证：JWT（PyJWT / python-jose）+ Cookie；bcrypt（passlib[bcrypt]）；RSA（cryptography）
- 媒体处理：Pillow（图片缩略图/大图/WebP）、ffmpeg（视频首帧，通过 subprocess 调用）
- 校验：pydantic v2（FastAPI 内置）
- 日志：标准 logging + RotatingFileHandler
- 代码检查：Ruff（lint + format）、Mypy（类型检查）
- 测试：pytest + TestClient（httpx）

### 前端
- React 18 + TypeScript 5
- 构建：Vite
- 状态管理：Zustand
- 组件库：animal-island-ui（CDN 加载，jsDelivr 镜像）
- 补充组件：Radix UI Primitives（无样式 + 自定义样式）
- 路由：React Router v6
- HTTP 客户端：fetch 封装（带 cookie credentials）
- 加密：JSEncrypt（RSA 加密密码）
- 代码检查：ESLint + Prettier + TypeScript

### 工程化
- Git Hooks：pre-commit 自动跑 Ruff+Mypy 与 ESLint+Prettier
- 启动脚本：`scripts/dev.sh` 同时启动前后端，Ctrl+C 全部退出
- 编译脚本：`scripts/build.sh` 一键编译前端并打包
- Docker：多阶段构建（前端 build → 后端镜像托管静态文件）
- 日志目录：`logs/`，前后端各一文件，自动轮转

## 三、数据库模型设计

### 表清单

1. **system_status**（系统状态，单行表）
   - `id` PK
   - `initialized` bool（初始化状态位）
   - `admin_user_id` int nullable（首个 admin）
   - `created_at`, `updated_at`

2. **users**
   - `id` PK
   - `email` str unique（登录凭证）
   - `password_hash` str（bcrypt）
   - `nickname` str
   - `signature` str nullable
   - `avatar_path` str nullable（头像相对路径，无则用默认头像）
   - `role` str（`admin` / `user`，默认 `user`）
   - `status` str（`active` / `deactivated` / `disabled`），默认 `active`
   - `can_invite` bool（是否允许生成邀请码，默认 True，admin 可改）
   - `failed_login_count` int 默认 0
   - `locked_until` datetime nullable
   - `last_login_at` datetime nullable
   - `created_at`, `updated_at`
   - 索引：`email` unique；`status`

3. **rsa_keys**（单行表，存 RSA 密钥对）
   - `id` PK
   - `public_key_pem` str
   - `private_key_pem` str（PEM 格式，本机存储；Docker 重建会重新生成，导致旧 token 失效，可接受）
   - `created_at`

4. **invite_codes**
   - `id` PK
   - `code` str unique（随机生成）
   - `creator_id` int FK users
   - `status` str（`active` / `used` / `expired` / `revoked`）
   - `expires_at` datetime（用户自选有效期）
   - `used_by_id` int FK users nullable
   - `created_at`
   - 约束：每个 creator 同一时间仅一个 `active` 状态邀请码（应用层校验 + 部分索引）
   - 索引：`creator_id`；`code` unique；`status`

5. **friendships**（好友关系，双向）
   - `id` PK
   - `user_a_id` int FK users
   - `user_b_id` int FK users
   - `status` str（`pending` / `accepted`）
   - `requester_id` int FK users（发起方）
   - `created_at`, `accepted_at` nullable
   - 约束：`user_a_id < user_b_id`（规范化存储，避免重复双向记录）；复合唯一索引 `(user_a_id, user_b_id)`
   - 查询好友：`(user_a_id=u AND user_b_id=f) OR (user_a_id=f AND user_b_id=u) AND status=accepted`

6. **posts**（朋友圈动态）
   - `id` PK
   - `user_id` int FK users
   - `content` str（文字）
   - `visibility` str（`public` / `friends`）
   - `deleted_at` datetime nullable（软删除）
   - `created_at`, `updated_at`
   - 索引：`user_id`；`created_at`（cursor 分页）；`deleted_at`（过滤软删）

7. **post_media**（动态媒体文件）
   - `id` PK
   - `post_id` int FK posts
   - `file_path` str（源文件相对路径）
   - `thumb_path` str（缩略图 WebP 相对路径）
   - `large_path` str（大图 WebP 相对路径，视频为空）
   - `filename` str（重命名后文件名）
   - `size` int（字节数）
   - `mime` str
   - `format` str（如 jpg/png/webp/mp4/mov）
   - `kind` str（`image` / `video`）
   - `sort_order` int
   - `created_at`
   - 索引：`post_id`

8. **comments**（评论）
   - `id` PK
   - `post_id` int FK posts
   - `user_id` int FK users
   - `parent_comment_id` int FK comments nullable（回复某条评论）
   - `reply_to_user_id` int FK users nullable（被回复者，用于「回复 @xxx」）
   - `content` str nullable（纯文字评论时可为空？需图片或文字至少一项）
   - `image_path` str nullable（评论图片源路径）
   - `image_thumb_path` str nullable
   - `image_large_path` str nullable
   - `deleted_at` datetime nullable（软删除）
   - `created_at`, `updated_at`
   - 索引：`post_id`；`created_at`

9. **likes**（点赞）
   - `id` PK
   - `target_type` str（`post` / `comment`）
   - `target_id` int
   - `user_id` int FK users
   - `created_at`
   - 唯一约束：`(target_type, target_id, user_id)`
   - 索引：`(target_type, target_id)`

10. **file_metadata**（可选：统一文件元数据，便于后期清理/审计）
    - `id` PK
    - `storage_path` str unique
    - `original_name` str
    - `filename` str
    - `size` int
    - `mime` str
    - `format` str
    - `kind` str（`image` / `video` / `avatar` / `thumb` / `large`）
    - `owner_id` int FK users nullable
    - `created_at`

### 关键设计说明
- 软删除统一用 `deleted_at` 字段，查询时 `WHERE deleted_at IS NULL` 过滤。
- 好友关系规范化存储（`user_a_id < user_b_id`），避免双向重复。
- 点赞用 `(target_type, target_id)` 多态关联，避免两张表。
- 邀请码「同时仅一个有效」用应用层逻辑 + 状态约束保证。

## 四、API 设计概览

所有 API 前缀 `/api/v1`，统一错误响应格式：

```json
{ "code": "ERROR_CODE", "message": "人类可读信息", "detail": {} }
```

### 端点清单

**系统**
- `GET /api/health` — 健康检查
- `GET /api/v1/system/initialized` — 查询是否已初始化（前端决定进初始化页还是登录页）
- `POST /api/v1/system/init` — 首次初始化，注册 admin（仅在未初始化时可用）
- `GET /api/v1/auth/rsa-public-key` — 获取 RSA 公钥（登录/注册前调用）

**认证与用户**
- `POST /api/v1/auth/register` — 注册（需邀请码；初始化接口除外）
- `POST /api/v1/auth/login` — 登录（RSA 密文密码）
- `POST /api/v1/auth/logout` — 登出
- `POST /api/v1/auth/refresh` — 刷新 token
- `GET /api/v1/me` — 当前用户信息
- `PATCH /api/v1/me` — 修改昵称/签名/密码
- `POST /api/v1/me/avatar` — 上传头像
- `GET /api/v1/users/{user_id}` — 查看他人主页信息
- `GET /api/v1/users/{user_id}/posts` — 他人主页动态列表
- `POST /api/v1/me/deactivate` — 自助注销

**邀请码**
- `POST /api/v1/invites` — 生成邀请码（自选有效期）
- `GET /api/v1/invites` — 我的邀请码列表/当前有效
- `POST /api/v1/invites/{id}/revoke` — 失效
- `POST /api/v1/invites/renew` — 续期（先失效当前再生成，或直接更新过期时间）

**好友**
- `POST /api/v1/friends/request` — 按邮箱搜索并发送好友请求
- `GET /api/v1/friends/requests` — 收到的好友请求
- `POST /api/v1/friends/requests/{id}/accept` — 接受
- `POST /api/v1/friends/requests/{id}/reject` — 拒绝
- `GET /api/v1/friends` — 好友列表
- `DELETE /api/v1/friends/{user_id}` — 删除好友

**朋友圈动态**
- `POST /api/v1/posts` — 发动态（文字 + 媒体，visibility）
- `GET /api/v1/feed` — 信息流（cursor 分页：全部公开 + 好友仅好友 + 自己全部）
- `GET /api/v1/posts/{id}` — 动态详情
- `DELETE /api/v1/posts/{id}` — 软删除（作者/admin）
- `GET /api/v1/posts/{id}/media/{media_id}/{spec}` — 访问媒体（spec: thumb/large/original，鉴权 + 防路径穿越）

**评论与点赞**
- `GET /api/v1/posts/{id}/comments` — 评论列表（offset 分页）
- `POST /api/v1/posts/{id}/comments` — 发评论（文字 / 单图，可回复某评论）
- `DELETE /api/v1/comments/{id}` — 软删除评论（作者/动态作者/admin）
- `POST /api/v1/posts/{id}/likes` — 点赞动态
- `DELETE /api/v1/posts/{id}/likes` — 取消点赞
- `POST /api/v1/comments/{id}/likes` — 点赞评论
- `DELETE /api/v1/comments/{id}/likes` — 取消点赞

**管理（admin）**
- `GET /api/v1/admin/stats` — 统计信息
- `GET /api/v1/admin/users` — 用户列表/搜索
- `PATCH /api/v1/admin/users/{id}` — 停用/启用用户、修改邀请权限、恢复账号
- `GET /api/v1/admin/posts` — 全站动态管理
- `DELETE /api/v1/admin/posts/{id}` — 删除任意动态
- `GET /api/v1/admin/invites` — 全站邀请码管理
- `GET /api/v1/admin/comments` / `DELETE /api/v1/admin/comments/{id}`

## 五、分阶段实现计划

> 阶段编号即实现顺序。每个阶段产出可独立验证的成果。前端在阶段 8 起进入正式开发，但阶段 6 起可并行搭建前端骨架。

### 阶段 0：工程脚手架与工具链

**目标**：搭好项目骨架，跑通前后端最小启动，工具链就位。

**任务清单**
1. 创建仓库目录结构（见第二章）。
2. 后端 `pyproject.toml`（uv 初始化），装好 FastAPI、uvicorn、gunicorn、SQLAlchemy、Alembic、PyJWT、passlib[bcrypt]、cryptography、Pillow、pydantic-settings、python-multipart 等。
3. `backend/app/config.py`：用 pydantic-settings 读取 `.env`，含 `JWT_SECRET`、`JWT_EXPIRE_DAYS=7`、`COOKIE_NAME`、`PUBLIC_BASE_URL`（邀请链接域名）、`STORAGE_ROOT`、`DB_URL`、`MEDIA_IMAGE_MAX_MB=40`、`MEDIA_VIDEO_MAX_MB=200` 等。
4. 初次启动逻辑：`.env` 不存在则从 `.env.example` 复制；`JWT_SECRET` 为空则自动生成并写回 `.env`。
5. `.env.example` 提供全部配置项示例与注释。
6. 前端 `frontend/`：Vite + React + TS 初始化，`index.html` 引入 animal-island-ui CDN（CSS + JS）。
7. 前端 ESLint + Prettier 配置；后端 Ruff + Mypy 配置（`pyproject.toml`）。
8. Git Hooks：`.githooks/pre-commit` 跑前端 lint、后端 ruff+格式化 + mypy；配置 `git config core.hooksPath .githooks`（README 说明）。
9. `scripts/dev.sh`：后台并行启动 `uv run uvicorn`（开发用 uvicorn --reload）与 `npm run dev`（Vite dev server），用 trap 捕获 SIGINT 全部 kill。
10. `scripts/build.sh`：前端 `npm run build` 生成 dist，拷到后端静态目录或由后端托管路径读取。
11. 日志配置 `backend/app/logging.py`：RotatingFileHandler 写 `logs/backend.log`；前端 dev 时 Vite 自带日志，生产由后端代理记录访问日志。
12. Dockerfile 多阶段构建骨架（先占位，后期填实）。
13. `.gitignore`：忽略 `data/`、`logs/`、`storage/`、`.env`、`node_modules`、`dist`、`__pycache__`、`.venv`。
14. `backend/app/main.py`：最小 FastAPI app + `GET /api/health` 返回 `{"status":"ok"}`。
15. FastAPI 静态托管：挂载 `frontend/dist` 到根路径（生产模式），API 路由前缀 `/api`。

**验收标准**
- `bash scripts/dev.sh` 能同时起前后端，访问 `http://localhost:8000/api/health` 返回 ok，前端 dev server 可访问。
- `bash scripts/build.sh` 能产出前端 dist。
- `.env` 不存在时首次启动自动生成。
- pre-commit 钩子能拦截 lint 错误。

---

### 阶段 1：数据库与 ORM 基础

**目标**：建立数据库连接、ORM 基类、Alembic 迁移框架，并创建基础表。

**任务清单**
1. `backend/app/database.py`：engine（SQLite，`check_same_thread=False`）、`SessionLocal`、`Base`、`get_db` 依赖。
2. 创建 `backend/app/models/` 下所有 ORM 模型（见第三章全部表），含字段类型、约束、索引。
3. Alembic 初始化 `alembic init`，配置 `env.py` 读取 `config.DB_URL` 并绑定 `Base.metadata`，支持 `autogenerate`。
4. 生成首个迁移 `alembic revision --autogenerate -m init`，`alembic upgrade head` 建表。
5. 启动时自动 `alembic upgrade head`（嵌入到 `main.py` startup，或 dev 脚本中执行）。
6. `system_status` 单行记录初始化（`initialized=False`）。
7. 内置 `assets/default_avatar.png`（占位，等需求方提供后替换）。

**验收标准**
- `alembic upgrade head` 成功建表，SQLite 文件生成。
- 所有表与索引与设计一致。
- `system_status` 存在初始行。

---

### 阶段 2：认证与用户系统（核心）

**目标**：完成初始化、注册、登录、个人资料、头像、注销。

**任务清单**
1. **RSA 密钥对**：`backend/app/core/security.py` 用 `cryptography` 生成 RSA-2048 密钥对，存 `rsa_keys` 表（单行）。启动时若无则生成。`GET /api/v1/auth/rsa-public-key` 返回 PEM 公钥。
2. **JWT 工具**：签发（7 天有效期）、解析、刷新逻辑；`JWT_SECRET` 从配置读。
3. **Cookie 工具**：设置 JWT cookie，`HttpOnly`、`SameSite=Lax`、`Secure`（生产，由配置控制）；Double Submit Cookie：另设一个非 HttpOnly 的 CSRF token cookie，前端读后放请求头 `X-CSRF-Token`，后端比对。
4. **依赖注入**：`get_current_user`（从 cookie 解 JWT → 查 user）、`require_admin`。
5. **初始化流程**：
   - `GET /api/v1/system/initialized` 读 `system_status.initialized`。
   - `POST /api/v1/system/init`：仅 `initialized=False` 可用；接收邮箱/昵称/密码（RSA 密文），解密→bcrypt→创建 user(role=admin)→更新 `system_status.initialized=True, admin_user_id=...`。
6. **注册** `POST /api/v1/auth/register`：需有效邀请码（校验 status=active 且未过期）；RSA 解密密码→bcrypt；创建 user(role=user, status=active)；标记邀请码 used。
7. **登录** `POST /api/v1/auth/login`：
   - RSA 解密密码。
   - 查 user；若 `status != active`（deactivated/disabled）拒绝。
   - 锁定检查：`locked_until` 未到则拒绝并提示剩余时间。
   - 密码 bcrypt 校验：失败则 `failed_login_count += 1`，到 5 则 `locked_until = now + 15min`；成功则清零并 `last_login_at = now`。
   - 签发 JWT 写 cookie + CSRF cookie。
8. **登出** `POST /api/v1/auth/logout`：清 cookie。
9. **刷新** `POST /api/v1/auth/refresh`：token 接近过期时续签（sliding expiry）。
10. **个人资料**：
    - `GET /api/v1/me`。
    - `PATCH /api/v1/me`：改昵称/签名/密码（改密码需验证旧密码）。
11. **头像上传** `POST /api/v1/me/avatar`：校验图片格式/大小（≤40M），按 `用户ID_时间戳_4位UUID` 命名存 `storage/avatars/`，生成缩略图 WebP（400px）；更新 `users.avatar_path`。旧头像文件保留不删。
12. **注销** `POST /api/v1/me/deactivate`：`status = deactivated`；评论保留展示。
13. **密码规则**：至少 8 位，含数字/字母/符号中至少两类（pydantic validator）。
14. **用户展示**：`GET /api/v1/users/{id}` 返回他人公开信息；`deactivated` 用户 nickname 显示「已注销」、avatar 用默认。

**验收标准**
- 初始化→admin 注册→登录→改资料→上传头像→登出 全流程跑通（用 curl/httpie 验证）。
- 登录失败 5 次后锁定 15 分钟。
- 注销后该用户在他人评论列表显示「已注销」+ 默认头像。
- CSRF：缺 `X-CSRF-Token` 的 POST 被拒。

### 阶段 3：文件与媒体系统

**目标**：完成上传、缩略图/大图生成、视频首帧、媒体访问（鉴权+防穿越）。

**任务清单**
1. **格式校验** `backend/app/storage/filekit.py`：用 Pillow/`filetype` 库校验真实图片格式（不只看后缀）；视频用 ffprobe/文件头校验；拒绝可执行文件。
2. **大小限制**：图片 ≤40M、视频 ≤200M，超限拒绝（413）。
3. **命名**：`时间戳_6位UUID.ext`；写入前检查目标路径是否存在（极小概率重复则重新生成）。
4. **存储路径**：`storage/media/YYYY-MM/`；头像 `storage/avatars/`。
5. **缩略图/大图生成**（BackgroundTasks）：
   - 图片：Pillow 生成缩略图（400px 等比、WebP 80%）、大图（2160px、WebP 90%）。
   - 视频：ffmpeg 取首帧 → 生成缩略图；大图留空（视频无大图）。
   - 原文件保留。
6. **上传接口**：动态媒体上传与评论图片上传均落 `storage/media/`；先同步落盘并返回 media_id，后台异步生成缩略图（前端首次访问可能需轮询或加载占位）。
7. **媒体访问** `GET /api/v1/posts/{post_id}/media/{media_id}/{spec}`：
   - `spec ∈ {thumb, large, original}`。
   - 鉴权：当前用户是否有权访问该 post（公开可见 or 好友 or 自己）。
   - 防路径穿越：从 DB 读 `media` 行的路径，绝不直接拼用户输入；用 `Path.resolve()` 校验仍在 `STORAGE_ROOT` 内。
   - 返回文件流，带正确 Content-Type；支持条件请求/缓存头。
   - 头像访问单独接口 `GET /api/v1/avatars/{user_id}`（公开，用于展示）。
8. **`file_metadata` 记录**：每次上传写一条元数据。

**验收标准**
- 上传图片生成 3 个规格文件（源/缩略图/大图）。
- 上传视频生成首帧缩略图。
- 非「仅好友」动态的媒体被无权用户直接 URL 访问返回 403。
- 路径穿越 `../../etc/passwd` 被拒。

### 阶段 4：朋友圈动态核心

**目标**：发动态、信息流、动态详情、删除、用户主页。

**任务清单**
1. `POST /api/v1/posts`：文字 + 媒体 ID 列表（媒体先单独上传拿到 ID）+ visibility；校验媒体归属当前用户且未被使用；绑定到 post。
2. `GET /api/v1/feed`：cursor 分页（`before=created_at,id`）。
   - 可见性过滤：`post.visibility=public` OR（`post.visibility=friends` AND 当前用户是作者好友）OR 作者=当前用户。
   - 过滤软删。
   - 返回每条动态的作者信息、媒体缩略图 URL、点赞数、评论数、当前用户是否点赞。
   - 信息流按 `created_at DESC, id DESC` 排序，cursor 用 `(created_at, id)` 组合。
3. `GET /api/v1/posts/{id}`：详情，含媒体、评论（首批）、点赞数。
4. `DELETE /api/v1/posts/{id}`：软删（`deleted_at=now`）；权限：作者本人或 admin。
5. `GET /api/v1/users/{id}/posts`：他人主页动态（受可见性约束：公开 + 好友仅好友；若 user_id=自己则全部）。
6. **XSS**：服务端对 `content` 做 HTML 转义（或前端渲染用文本节点/`dangerouslySetInnerHTML` 之外的方式）；前端也做转义。

**验收标准**
- 发含 3 图的公开动态，信息流能看到。
- 好友的「仅好友」动态自己能看到，非好友看不到。
- cursor 分页正确，不重复不漏。
- 作者删自己的动态后信息流不再出现。
- 文字含 `<script>` 不被执行。

### 阶段 5：评论与点赞

**目标**：链式评论（平铺+回复引用）、评论图片、点赞 toggle。

**任务清单**
1. `GET /api/v1/posts/{id}/comments`：offset 分页（`page, page_size`，默认 20）。
   - 可见性约束：若 post 是「仅好友」，则评论作者必须是 post 作者的好友才能被当前用户看到；具体规则：当前用户 C 能看到的评论 = 评论作者 U 与 post 作者 A 是好友，或 U == C，或 U == A。（A 发仅好友动态，B 是 A 好友评论，C 是 A 好友但非 B 好友 → C 看不到 B 评论）
   - 平铺返回，含 `parent_comment_id`、`reply_to_user` 信息供前端显示「回复 @xxx」。
   - 软删评论返回占位（如显示「该评论已删除」或直接过滤，按产品定——本期过滤）。
2. `POST /api/v1/posts/{id}/comments`：文字 或 单张图片（二选一或图片为主、文字可选）；可带 `parent_comment_id` + `reply_to_user_id`。
   - 鉴权：当前用户是 post 作者好友 或 post 公开 或 自己的 post（按可见性：能看 post 才能评论——实际只要能看就能评）。
3. `DELETE /api/v1/comments/{id}`：软删；权限：评论作者 / post 作者 / admin。
4. 点赞：
   - `POST/DELETE /api/v1/posts/{id}/likes`、`/api/v1/comments/{id}/likes`。
   - 唯一约束防重复；toggle 语义（已赞则取消）。
   - 不发通知。
5. 返回评论时附带 `like_count`、`liked_by_me`。

**验收标准**
- A 发仅好友动态，B(A 好友)评论，C(A 好友但非 B 好友)看不到 B 评论。
- 回复评论时前端显示「回复 @B」。
- 评论带 1 张图能上传并展示缩略图。
- 点赞→再点取消，计数正确。

### 阶段 6：好友系统

**目标**：按邮箱搜索加好友、双向确认、删除好友、好友列表，并打通可见性。

**任务清单**
1. `POST /api/v1/friends/request`：按 email 精确搜索（仅返回是否存在+基本信息，或直接发起请求）；规范化存 friendships（`user_a_id<user_b_id`，`requester_id`，`status=pending`）。
2. `GET /api/v1/friends/requests`：收到的 pending 请求。
3. `POST /api/v1/friends/requests/{id}/accept`：`status=accepted, accepted_at=now`。
4. `POST /api/v1/friends/requests/{id}/reject`：删除该 pending 行。
5. `GET /api/v1/friends`：好友列表（status=accepted）。
6. `DELETE /api/v1/friends/{user_id}`：删除好友关系（删行）。
7. 封装 `are_friends(user_a, user_b)` 工具，供阶段 4/5 可见性逻辑复用。
8. 搜索邮箱时注意隐私：仅对「精确匹配且存在」返回可加好友，不泄露用户列表。

**验收标准**
- A 搜索 B 邮箱发请求 → B 接受 → 互为好友。
- 删除好友后，「仅好友」动态对对方不可见。
- 已是好友重复请求被拒。

### 阶段 7：邀请系统

**目标**：邀请码生成/失效/续期/邀请链接，注册消费邀请码。

**任务清单**
1. `POST /api/v1/invites`：生成随机码（如 8-12 位 base32）；自选有效期（如 1/7/30 天或不限期）；校验当前无 active 邀请码（否则提示先失效或自动失效旧的）。
2. `GET /api/v1/invites`：返回我的当前有效邀请码 + 历史。
3. `POST /api/v1/invites/{id}/revoke`：标记 revoked。
4. `POST /api/v1/invites/renew`：续期（更新 expires_at 或先 revoke 旧的再建新的，按实现选一）。
5. 邀请链接：`{PUBLIC_BASE_URL}/register?invite={code}`，`PUBLIC_BASE_URL` 来自环境变量。
6. 注册接口校验邀请码（阶段 2 已实现，此处补充续期/管理细节）。
7. admin 可关闭某用户的 `can_invite`（阶段 8），关闭后该用户不能生成新邀请码。

**验收标准**
- 每人同时仅一个 active 邀请码。
- 过期邀请码注册被拒。
- 用邀请链接注册成功后该码标记 used。

### 阶段 9：前端开发

**验收标准**
- 桌面端与移动端布局自适应。
- 登录→发动态→评论→点赞→加好友→管理 全流程可用。
- 用户输入 `<script>` 不执行。
- `npm run build` 产出带 .br/.gz 压缩文件。

- **安全**：贯穿全部阶段，见设计文档第八节（文件校验、防穿越、鉴权、密码、CSRF、登录锁定）。
