### 3.3 评论可见性工具（扩展 `backend/app/utils/visibility.py`）

新增函数：

```python
def can_view_comment(db, viewer_id: int, comment: Comment, post: Post) -> bool:
    """评论可见性：
    - 评论软删 -> False
    - post 软删 -> False
    - post 公开 -> True（任何登录用户可见）
    - post 仅好友 -> 评论作者 U 需满足：
        U == viewer（自己发的）
        或 U == post 作者（动态本人）
        或 U 与 post 作者 A 是好友 且 U 与 viewer 无要求（见下）
      当前用户 C 能看到评论 = (U == C) or (U == A) or (are_friends(A, U))
      简言之：在仅好友动态下，评论作者必须是动态作者的好友（或本人/作者），
      该评论才对该动态的任何可见者（C 也是 A 的好友或 C 是作者本人）可见。
    """
```

依据阶段 5 验收标准：A 发仅好友动态，B(A 好友)评论，C(A 好友但非 B 好友)看不到 B 评论。
=> 判定 = `U==C or U==A or are_friends(A,U)`。

注意：列表场景需要批量判定，逐条 `can_view_comment` 会 N 次查好友。本方案在 service 层用集合批量预取 post 作者的好友 ID 集合，再逐条过滤，避免 N 次查询。

### 3.4 评论服务（新建 `backend/app/services/comment_service.py`）

函数清单：

1. `list_comments(db, viewer_id, post_id, page, page_size) -> dict`
   - 校验 post 存在且 `can_view_post`（否则 404/403）。
   - 查评论 `Comment.post_id == post_id AND deleted_at IS NULL`，按 `created_at ASC, id ASC` 排序（平铺，类似微博）。
   - offset 分页：`offset = (page-1)*page_size`，`limit = page_size`，`total = count(*)`。
   - 批量加载：评论作者 users、reply_to users、当前用户点赞集合、点赞计数。
   - 若 post.visibility == "friends"：预取 `friend_ids_of_author = are_friends 集合`；过滤评论，仅保留 `comment.user_id in ({viewer_id, post.user_id} | friend_ids_of_author)`。
   - 软删评论直接过滤（本期不返回占位）。
   - `image_thumb_url = /api/v1/comments/{comment_id}/media/thumb`、`image_large_url = /api/v1/comments/{comment_id}/media/large`（鉴权访问，见 3.6）。
   - `can_delete = (comment.user_id == viewer_id) or (post.user_id == viewer_id) or (viewer.role == "admin")`。
   - 返回 `CommentListOut`。

2. `create_comment(db, user, post_id, data) -> dict`
   - 校验 post 存在（deleted_at IS NULL）。
   - `can_view_post(db, user.id, post)` 否则 403（能看才能评）。
   - 校验非空：`content.strip()` 或 `media_id` 至少一个；否则 `EMPTY_COMMENT`。
   - 若 `media_id`：查 `PostMedia`，校验 `owner_id == user.id` 且 `post_id IS NULL`（未绑定）且 `kind == "image"`（评论不支持视频）；绑定方式：**不绑定到 post**，而是在创建 comment 后把该 media 的 file_path/thumb_path/large_path 复制到 comment 的 image_* 字段，并保留 media 行（或标记）。简化方案：评论图片**直接在 service 内同步处理**（不走 BackgroundTasks），即上传时同步生成 thumb/large 并写入 comment.image_*。→ 采用方案 A：复用 `/api/v1/media/upload` 上传拿到 media_id（已同步落盘，后台异步生成 thumb），评论创建时读取 media 的 file_path/thumb_path/large_path 写入 comment；若 thumb_path 尚未生成（后台未完成），则 image_thumb_url 为空，前端可轮询或直接显示原图。**为避免评论图片显示空白，评论图片上传走独立端点 `POST /api/v1/comments/media`，同步生成 thumb/large**（评论图片单张、体积小，同步处理可接受）。
     - 最终采用：新增 `upload_comment_image(db, user, file)`，同步落盘 + 同步 Pillow 生成 thumb/large WebP，返回 `media_id`（仍写一条 `PostMedia` 行，`post_id=None`，作为评论图片载体）。创建评论时根据 `media_id` 读取其 file_path/thumb_path/large_path 写入 comment，并把 media 标记 `post_id = -1`（哨兵值表示「已用于评论」）避免被动态复用。→ 更简洁：直接在 comment.image_* 存相对路径，不再依赖 PostMedia 行；上传端点同步返回 thumb/large 的相对路径给前端？但前端只需 media_id。→ 采用：上传端点返回 `media_id`；创建评论时 service 读 PostMedia 拿三条路径写入 comment，并把 PostMedia.`post_id` 设为 `-1`（哨兵）防复用。
   - 若 `parent_comment_id`：校验该评论存在且属于同一 post 且未软删；`reply_to_user_id` 校验该用户存在；若 `parent_comment_id` 提供但 `reply_to_user_id` 缺省，则取 parent.user_id。
   - 创建 `Comment`，commit，返回 `CommentOut`（单条）。
   - 注意：评论图片不绑定到 `posts`，媒体访问端点需对 comment 图片独立处理。

3. `delete_comment(db, user, comment_id) -> None`
   - 查评论（含已软删？已软删返回 404）。
   - 权限：`comment.user_id == user.id` 或 `post.user_id == user.id` 或 `user.role == "admin"`；否则 403。
   - `comment.deleted_at = now`，commit。

4. `get_comment_image(db, viewer_id, comment_id, spec) -> tuple[Path, str]`
   - 查评论（含软删？软删的评论图片不可访问，返回 404）。
   - 校验 spec ∈ {thumb, large}（评论图片不提供 original 访问，避免大图泄露；或提供 original 也可——本方案提供 thumb/large/original 三档，与动态一致，便于前端点开看原图）。
   - 鉴权：查 post，`can_view_post(db, viewer_id, post)`。
   - 根据 spec 取 `image_thumb_path` / `image_large_path` / `image_path`；`resolve_within_storage`；返回 (abs_path, mime)。

### 3.5 点赞服务（新建 `backend/app/services/like_service.py`）

```python
def toggle_post_like(db, user, post_id) -> dict
def toggle_comment_like(db, user, comment_id) -> dict
def _toggle(db, user, target_type, target_id) -> dict
```

- `toggle_post_like`：校验 post 存在（deleted_at IS NULL）且 `can_view_post`。
- `toggle_comment_like`：校验评论存在（deleted_at IS NULL）、其 post 存在且 `can_view_post`，且评论对当前用户可见（`can_view_comment`）。
- toggle 语义：查 `Like(target_type, target_id, user_id)`；存在则删除（取消），不存在则插入。因有唯一约束，并发插入会触发 IntegrityError，捕获后按「已存在」处理（删除）。
- 返回 `LikeCountOut`：重新查询 `like_count` 与 `liked_by_me`，确保准确。
- 端点用 POST（点赞/取消合一），命名 `/api/v1/posts/{id}/likes` 与 `/api/v1/comments/{id}/likes`，返回 `LikeCountOut`。DELETE 语义也保留（按设计文档 `POST/DELETE`），本方案采用 **POST toggle** 简化前端，同时提供 DELETE 作为「仅取消」的别名（调用同一 toggle）。→ 为与设计文档一致且语义清晰，采用：`POST` = toggle，`DELETE` = 仅取消（不存在则 404 或幂等 204）。**最终决定：POST = toggle，返回 LikeCountOut；不单独实现 DELETE**（前端只调 POST）。后端只暴露 POST toggle 即可满足验收（点赞→再点取消，计数正确）。

### 3.7 评论图片上传（同步处理）

`comment_service.upload_comment_image(db, user, file)`：
- 复用 `filekit.detect_kind` + `validate_image` + `check_size`（仅 image，video 拒绝）。
- 落盘到 `storage/media/YYYY-MM/`，文件名 `时间戳_6位UUID.ext`。
- 同步 Pillow 生成 thumb（400px WebP80）+ large（2160px WebP90），写入 `PostMedia` 行（`post_id=None`, `owner_id=user.id`, `kind="image"`，填 file_path/thumb_path/large_path）。
- 写 `FileMetadata`。
- 返回 `{media_id, image_thumb_url: None（URL 由 comment 返回）, status: "ready"}`。

创建评论时读取该 media 行，把 file_path/thumb_path/large_path 写入 `Comment.image_path/image_thumb_path/image_large_path`，并把 `PostMedia.post_id` 设为 `-1`（哨兵，防止被动态 create_post 复用——create_post 里检查 `m.post_id is not None` 会拒绝，但哨兵 -1 也会被拒绝，符合预期）。

## 六、验收对照

- A 发仅好友动态，B(A 好友)评论，C(A 好友但非 B 好友)看不到 B 评论 → `can_view_comment` + 用例 6。
- 回复评论时前端显示「回复 @B」→ `CommentOut.reply_to` + 前端渲染。
- 评论带 1 张图能上传并展示缩略图 → 评论图片上传端点 + CommentOut.image_thumb_url。
- 点赞→再点取消，计数正确 → toggle 语义 + 用例 8/9。

## 八、注意事项

- 评论图片上传走同步处理（单图、体积小），避免后台异步导致评论创建时 thumb 未生成。
- 评论图片 PostMedia 行 `post_id` 用 `-1` 哨兵防止被动态复用；create_post 的 `m.post_id is not None` 校验会拒绝 `-1`，符合预期。
- toggle 点赞需处理唯一约束并发：`try: db.add(like); db.commit() except IntegrityError: db.rollback(); 删除已存在的 like`。
- `can_view_comment` 的批量版本：在 `list_comments` 内一次性取出 post 作者的好友 ID 集合，避免 N 次查询。
- 软删评论不在列表返回；其图片访问返回 404。
- XSS：服务端不额外转义（前端用文本节点），但 `content` 长度限制 2000。
- 评论列表排序 `created_at ASC`（平铺，微博式）；分页 offset。
- `like_count` / `liked_by_me` 在评论列表与 toggle 响应中均返回。
